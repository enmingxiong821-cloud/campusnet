## 一、结论摘要

1. **本校（西北农林科技大学）用的是深澜 SRUN 体系**：浏览器页面挂在
   `http://172.26.8.11/srun_portal_pc?ac_id=1&theme=pro`，成功页是 `/srun_portal_success`，
   协议端点是 `/cgi-bin/get_challenge` 与 `/cgi-bin/srun_portal`，会话查询是
   `/cgi-bin/rad_user_info`。本项目 `srun.py` 已实现同一条链路，并在真实门户上验证过。
2. **「浏览器验证登录」不等于必须开浏览器**：页面登录区由 JS 渲染、提交按钮是
   `<button type="button" id="login-account">` 而不是 `submit`，所以浏览器模式要留；但底层可用
   纯 HTTP 复现，成本低得多。同校开源项目 `CNYoki/NWAFU-wifi-login-script` 里那套 selenium 方案，
   作者自己在 README 里标注了「不建议使用」。
3. **同类项目里最值得对照的不是同校脚本，而是两个把工程做完整的实现**：
   `Mmx233/BitSrunLoginGo`（跨平台/容器/路由器的分发方式）与 `Georgeupup/szu-network-guardian`
   （守护、凭据、直连、日志、自启的完整取舍）。

### 2.4 同类「完整工程」对照（最值得读的两个）

**`Georgeupup/szu-network-guardian`（Python，深圳大学，34★）**

功能集与本项目高度重叠，但取舍更偏「无人值守」：

- 教学区 SRun 与宿舍区 ePortal 两套体系并存，**手动选区域**，理由是「网关互通会造成误判」；
  另提供实验性的顺序尝试模式。→ 同一所学校多套认证并存是普遍问题。
- **强制直连**绕过 Clash/Mihomo/V2Ray 的 TUN/Fake-IP，避免代理造成在线误判。
- 用**两个独立且不可缓存的外网请求**复核连通性，避免单个检测页造成假在线。
- 即使白名单网页可打开，也**优先核验 SRun 会话**，认证失效立即重连。
- 仅在断网时登录，不在联网正常时重复认证；认证成功后**分阶段复查**再报成功。
- 凭据用 Windows DPAPI 保存；日志按天保存并清理 7 天前；界面只留最近 3 小时。
- PyInstaller 单文件 EXE + GitHub Actions 自动构建。
- 明确写了边界：「本程序负责网络链路建立后的校园网认证」，拔网线/关 Wi-Fi 需用户自行恢复。

**`Misyra/Campus-Auth`（Python，116★；已迁移到 Rust 版）**

- 基于 Playwright 的浏览器自动化，配合 Web 控制台（FastAPI + Vue3）。
- **用 JSON 描述认证步骤的任务系统**，可导入导出；这是把「浏览器登录」做成可配置规则而不是
  硬编码的一条可行路线。
- **多网络配置方案**：为不同网络建独立配置，按网关 IP 或 SSID 自动切换。
- 防重复启动同时检测 PID 文件与本地端口；暂停时段；失败退避重试。
- 提供 `start.exe`（自动装 uv 与依赖）与 `update.exe`（自动克隆/更新仓库），把「普通用户装不上
  Python 环境」这个门槛直接消掉。

## 三、可借鉴清单（对照本项目现状）

### 3.1 本项目已有，无需重复

- SRUN 的 challenge + HMAC-MD5 + xxtea 加密、`rad_user_info` 会话复核。
- 强制直连（`_build_opener` 不读 `http_proxy`），与 szu 项目的「强制直连」同源。
- 凭据加密：Windows 走 DPAPI，其它平台走本地密钥文件 + HMAC。
- 门户会话复核挡假掉线；仅在探活失败时才复核会话。
- 地址回退：`/eportal/...` 与 `/srun_portal_pc` 两类形态都有处理与回归测试。
- 三平台自启动载体（启动文件夹 / systemd user / LaunchAgent）。
- 浏览器模式的选择器猜测（字段名、placeholder、可填写性判断）。

### 3.2 值得补（按优先级）

1. **多目标连通性复核**（szu）：单个 canary 被 CDN 拦就会产生「在线未确认」，应改为一组目标
   （含不可缓存请求），任一放行即算通。
2. **防重复启动接进入口**（szu + Campus-Auth 都做了）：本项目 `lockfile.py` 已实现且有测试，
   但没有被 `serve()` 调用。
3. **单文件分发**（szu 的 PyInstaller + Actions；BitSrunLoginGo 的 Docker）：「几乎所有高校适用」
   的瓶颈之一是普通用户没有 Python 环境。
4. **多网络配置方案**（Campus-Auth）：按网关 IP / SSID 切换不同 profile，正好与「门户规则包」
   是同一层设计。
5. **暂停时段**（Campus-Auth）：夜间宿舍断网时不必反复重连。
6. **日志按天落盘并保留 N 天**（szu）：目前只有 SQLite 事件表与自启动重定向日志。
7. **systemd timer 的保活思路**（同校脚本）：比常驻进程更省资源，可作为 Linux 上「认证成功后
   退出、定时再查」的一种可选形态。

### 3.3 明确不借鉴

- `asche910/FreeWireless`（136★）等「绕过认证免费上网」类项目：属于规避计费，与本项目
  「用自己的账号自动认证」的定位不同，也有合规风险。
- `Zaxk1337/Eportalcutdown`、`admintony/ePortalGetPass` 等漏洞利用/枚举工具：仅作协议理解，
  不引入任何实现。

## 四、边界：本项目不做、也不该做的

以下体系在开源社区都有成熟实现，但它们的**生效层级**与本项目不同，应作为「明确不支持」写进
文档，而不是试图兼容：

| 体系 | 代表项目 | 为什么不做 |
|---|---|---|
| 802.1X / EAPoL | `tr3ee/go-rjsocks`、`gmsj0001/shnu-h3c`、`LoveElysia1314/sysu-netauth`、`zfx-t/openwrt-ruijie-minieap` | 需要网卡驱动层、证书、管理员权限，部分学校还禁用第三方客户端 |
| PPPoE 拨号 | 各家路由器脚本 | 需要 root 或系统拨号配置，不属于 Web 认证 |
| 客户端强管控（MAC 绑定、心跳） | 各校专有客户端 | 越界且有合规风险 |
