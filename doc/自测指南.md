# 自测指南

不需要真的掉线就能验证完整链路。配套 `utils/mock_portal.py` 在本机模拟一套
Dr.COM 形态的校园网门户，掉线、登录、复检、恢复全部可复现。

---

## 一、最快路径：三步跑完

开两个命令行窗口。

### 窗口 A —— 启动假校园网

```
cd C:\Users\Caspian6610\Desktop\校园网自连
python utils\mock_portal.py --drop
```

看到这行说明起来了：

```
本地模拟校园网已启动
  门户页面  http://127.0.0.1:2270/eportal/portal/login
  探测地址  http://127.0.0.1:2271/probe
  控制台    http://127.0.0.1:2270/admin
  初始状态  掉线
  账号/密码  20240001 / campus@2024
```

### 端口被占了怎么办

如果看到这行，说明 2270 或 2271 被别的程序占着（多半是上一轮忘了关）：

```
[错误]   端口 2270（门户）已被占用，占用者：PID 30916（多半是上一个没关掉的实例）
  端口 2271（探测）已被占用，占用者：PID 30916（多半是上一个没关掉的实例）
        端口被占时新开一个终端跑：
          python mock_portal.py --portal-port 2290 --probe-port 2291
        或先关掉占用它的那个程序。
```

三种应对，任选一种：

```
# 1) 直接换端口（提示里给的就是这条命令）
python utils\mock_portal.py --portal-port 2290 --probe-port 2291

# 2) 让它自己找空闲端口
python utils\mock_portal.py --auto-shift

# 3) 关掉占用的旧进程
taskkill //PID 30916 //F
```

> **重要**：如果你没改端口就跑 `check`，而旧的 mock 实例还在跑，
> 你会看到 `[OK]` 和退出码 0 —— 那是连上了旧实例的假绿灯。
> 测之前先确认 `/admin` 显示的状态是你刚设置的那个。

### 窗口 B —— 建号并立即检测

```
python utils\run.py add --name 模拟账号 ^
  --portal http://127.0.0.1:2270/eportal/portal/login ^
  --probe http://127.0.0.1:2271/probe ^
  --username 20240001 --password campus@2024 ^
  --password-mode base64 --login-mode http

python utils\run.py check
```

**期望输出**：

```
[OK ] 模拟账号: logged_in - 登录成功且网络已放行 (...s)
```

此例为模拟门户初始掉线、随后登录且复检放行，退出码为 `0`；耗时因环境而异。
如果模拟门户已经放行，首次也可能是 `online`，不会再次登录；先检查
`http://127.0.0.1:2270/admin` 的初始状态。若结果是 `FAIL`，记录退出码、
`state` 与事件日志，不能把 `FAIL` 当作预期的成功提示。
`logged_in` 表示本轮登录后探活确认放行；日志应能看到 `probe` 阶段的失败
和后续 `login`/`verify` 阶段的处理。

再检测一次通常会看到 `[OK ] 模拟账号: online - 网络已放行 (...s)`，
`state` 变成 `online`，表示检测前就已在线、这一轮没有触发登录。

### 窗口 C（可选）—— 开控制台看进度

```
python utils\run.py serve
```

浏览器打开 <http://127.0.0.1:2268>，点「立即检测」，顶部会实时滚动阶段：

```
start   开始检测 模拟账号
probe   正在探测 http://127.0.0.1:2271/probe
offline 检测到掉线（redirected），准备登录重连
retry   第 1/2 次尝试登录
connect 正在连接认证门户
parse   门户已响应（HTTP 200），正在识别登录表单
submit  以 POST 提交账号 20240001，账号框=DDDDD 密码框=upass，附加字段 user_ip,user_mac,0MKKey
verify  门户已受理，正在复检网络是否放行
done    登录成功，网络已放行
```

再点一次「立即检测」，这次会看到 `done 网络已放行，无需登录` —— 因为已经在线了。

## 二、反复测掉线恢复

模拟门户带一个开关页面：<http://127.0.0.1:2270/admin>

点「切换 放行 / 掉线」就能反复制造掉线。

推荐节奏：

1. 控制台点「立即检测」→ 看到 `logged_in`
2. 切到「掉线」
3. 再点「立即检测」→ 看到从 `offline` 到 `done` 的完整重连链路

命令行等价操作：

```
# 切掉线
curl -X POST http://127.0.0.1:2270/admin/toggle

# 切放行
curl -X POST "http://127.0.0.1:2270/admin/toggle?online=1"
```

## 三、逐项验证各功能

### 探活判定

```
python -c "import sys; sys.path.insert(0,'project/backend'); from campusnet.probe import probe; r=probe('http://127.0.0.1:2271/probe'); print(r.online, r.status, r.detail)"
```

掉线时应输出 `False redirected HTTP 302 -> http://127.0.0.1:2270/eportal/...`

### 密码错误路径

模拟门户会校验 Base64 密码。故意写错看失败反馈：

```
python -c "import sys; sys.path.insert(0,'project/backend'); from campusnet.storage import Account; from campusnet.portal import login; a=Account(name='x',portal_url='http://127.0.0.1:2270/eportal/portal/login',probe_url='http://127.0.0.1:2271/probe',username='20240001',password='wrong',password_mode='base64'); r=login(a); print(r.state, r.message)"
```

期望 `failed`，且模拟门户日志出现「密码错误」。

### GB2312 页面解码

模拟门户页面是 GB2312 编码，专门验证 charset 修复：

```
python -c "import sys; sys.path.insert(0,'project/backend'); from campusnet.portal import _fetch,_opener; from http.cookiejar import CookieJar; s,b,u,h=_fetch(_opener(CookieJar()),'http://127.0.0.1:2270/eportal/portal/login'); print('中文解码正确:', '校园网用户认证' in b)"
```

期望 `True`。若显示 False，说明 GBK 解码坏了。

### 门户自动发现

```
python utils\run.py discover --seed http://127.0.0.1:2271/probe --no-scan
```

期望识别出厂商 `Dr.COM / 深澜`、账号框 `DDDDD`、密码框 `upass`，
并打印出可直接复制的一键建号命令。

### 事件日志

```
python utils\run.py events --limit 20
```

期望看到 `probe` 阶段的 warning 与 `login` 阶段的 success 交替出现。

### 后台自动监控

```
python utils\run.py serve
```

然后把模拟门户切到掉线，等 60 秒（默认间隔）。控制台应自动出现重连进度，
无需手动点任何按钮。若想更快，把设置页的监控间隔改成 10 秒。

## 六、在真实校园网上测

模拟环境全绿不代表真实门户能用。真实测试流程：

1. 先保持与校园网的物理连接。仅拔网线或断开 Wi-Fi 会让门户也不可达，
   不能验证登录；在学校允许的情况下退出门户会话，使设备处于「连着校园网、
   尚未认证」状态。勿在教学/考试等关键时段测试。
2. 未认证时运行：

   ```
   python utils\run.py discover
   ```

   它会扫网关、识别厂商、提取字段名，并给出可直接复制的建号命令。

3. 按输出建号
4. `python utils\run.py check`：观察登录结果和随后探活是否放行；若是
   `online`，可能本来已有会话，不能据此断言本轮重新登录成功。
5. 通了再 `python utils\run.py serve` 长期运行

若 `discover` 没识别出来，先记录脱敏后的门户地址、页面结构和所需字段，
再选择登录方式。普通表单可能还需要字段名、隐藏参数或运营商选择；
验证码、短信、扫码需人工介入，不能保证无人值守。

### 真机验收清单（逐个设备/系统记录日期与结论）

| 检查项 | 期望现象 | 失败时先看 |
|---|---|---|
| Windows 登录自启动 | 重启并登录后 `/healthz` 可访问，监控有检测记录；`pythonw` 不弹控制台 | `bootstart status`、`database/autostart.log`、`/api/monitor` |
| Linux 用户级自启动 | 登录后服务运行；systemd 模式另核对 `systemctl --user is-enabled campusnet.service`，无 systemd 时核对 XDG 项 | `bootstart status`、用户级 journal / 桌面会话日志 |
| macOS LaunchAgent | 登录后服务运行且可看到检测记录 | `bootstart status`、`database/autostart.log`、LaunchAgent 状态 |
| Wi-Fi 未认证→重连 | 保持关联 Wi-Fi，退出门户会话后触发检测，复检确认放行 | `events --limit 20` 的 `probe`、`portal_state`、`login`、`verify` 阶段 |
| 仅有线及有线/Wi-Fi 切换 | 分别确认当前走的网络接口，认证后探活放行；切换后仍能检测 | 探活与门户事件、网卡 IP/路由，VPN/热点是否提供另一条出口 |
| 浏览器模式（CAS/验证码） | 真浏览器可完成页面流程；要求人工验证时明确提示 | `login`/`verify` 阶段与浏览器控制台，勿记录 Cookie/验证码 |

每项只记录「通过/未通过/未测」与脱敏后的现象，不要附账号、密码、令牌、
Cookie 或完整抓包。当前在单个平台上的验证不能代替其他平台的重启实测。

**遇到验证码**：模拟门户没有验证码，真实门户有。把登录方式改成
「浏览器登录（Playwright）」，需要先安装：

```
python -m pip install playwright
python -m playwright install chromium
```

纯图片验证码仍需人工介入 —— 这种情况程序会明确报出来，不会假装成功。
